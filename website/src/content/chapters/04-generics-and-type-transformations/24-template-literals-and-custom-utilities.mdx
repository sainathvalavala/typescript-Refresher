> 📖 **The problem.** TaskFlow has a tiny event system: `emitter.on("task:created", handler)`. A teammate writes `emitter.on("task:create", handler)` (missing the `d`). It compiles, because the event name is typed `string`, and the handler simply never fires. Nobody notices until a notification fails to appear in production.

Strings carry a lot of structure: `"task:created"` is a *namespace*, a colon, and an *action*. This chapter shows how to describe that structure in the type system with **template literal types**, how to transform string types (`Uppercase`, `Capitalize`), and how to combine them with mapped and conditional types to build **your own utility types**, and, just as important, how to know when to stop.

> 🧠 **Mental model.** **Template literal types are string templates evaluated by the type checker.** Combined with mapped and conditional types they let you build your own type tools. They also create a responsibility: stop before it gets clever.

## 24.1 Template literal types

A template literal type looks like a JavaScript template string, but it sits in type position and builds a *string type*:

```ts
type Entity = "task" | "project";
type Action = "created" | "deleted";

type EventName = `${Entity}:${Action}`;
// "task:created" | "task:deleted" | "project:created" | "project:deleted"
```

When you interpolate unions, TypeScript produces the **cross product**: every combination of every member. Two entities times two actions gives four event names, and you wrote none of them by hand. Add `"user"` to `Entity` and two more appear.

```ts
function emit(event: EventName): void {
  console.log("emit", event);
}

emit("task:created");  // ✅
emit("task:create");   // ❌ Argument of type '"task:create"' is not assignable to parameter of type '"project:created" | "project:deleted" | "task:created" | "task:deleted"'.

type CssLength = `${number}px` | `${number}rem`;
const w: CssLength = "12px";   // ✅
const bad: CssLength = "12em"; // ❌ Type '"12em"' is not assignable to type 'CssLength'.
```

The typo from the opening is now a compile error. You can interpolate `string`, `number`, `boolean`, and literal unions; with `string` you describe a *pattern* rather than a fixed set:

```ts
type ApiPath = `/api/${string}`;
const ok: ApiPath = "/api/tasks";      // ✅
const nope: ApiPath = "/tasks";        // ❌ Type '"/tasks"' is not assignable to type '`/api/${string}`'.
```

Beware of explosion: the cross product multiplies. Three unions of ten members each make a thousand-member union, and the compiler has a hard limit (about 100,000 members).

## 24.2 Intrinsic string types

Four built-in types transform string literal types. They are called **intrinsic** because the compiler implements them directly (you can't write them with other types):

```ts
type Loud = Uppercase<"task">;          // "TASK"
type Quiet = Lowercase<"TASK">;         // "task"
type Title = Capitalize<"task">;        // "Task"
type Camel = Uncapitalize<"TaskName">;  // "taskName"
```

They distribute over unions and combine naturally with template literals:

```ts
type Field = "title" | "done";

type Setter = `set${Capitalize<Field>}`;       // "setTitle" | "setDone"
type EnvVar = `TASKFLOW_${Uppercase<Field>}`;  // "TASKFLOW_TITLE" | "TASKFLOW_DONE"

function call(method: Setter) {}
call("setTitle"); // ✅
call("settitle"); // ❌ Argument of type '"settitle"' is not assignable to parameter of type '"setDone" | "setTitle"'.
```

These transformations apply to the **type**; at runtime a string is still just a string. The type checker doesn't change your value, it only verifies that the literal you wrote matches the pattern.

> 💡 **Tip.** You can also *pattern match* strings with `infer`, which makes template literals a mini parser (see the block below). Use it sparingly (see 24.6).

```ts
type Split<S> = S extends `${infer Ns}:${infer Act}` ? [Ns, Act] : never;
type Parts = Split<"task:created">; // ["task", "created"]
```

## 24.3 Key remapping with template literals

[Chapter 22](/chapter/22) introduced `as` in mapped types. Template literals are what make it truly useful: you can generate whole families of property names from a single object type.

```ts
interface Task {
  title: string;
  done: boolean;
}

type ChangeHandlers<T> = {
  [K in keyof T as `on${Capitalize<string & K>}Change`]: (next: T[K]) => void;
};

type TaskHandlers = ChangeHandlers<Task>;
// { onTitleChange: (next: string) => void; onDoneChange: (next: boolean) => void }

const handlers: TaskHandlers = {
  onTitleChange: (next) => console.log(next.toUpperCase()), // next: string
  onDoneChange: (next) => console.log(next ? "done" : "open"), // next: boolean
};
```

The same idea builds getters, setters, and "changed" events from one source type. Add `priority: number` to `Task` and `onPriorityChange` appears with the right parameter type.

```ts
type Events<T> = { [K in keyof T as `${string & K}Changed`]: { from: T[K]; to: T[K] } };
type TaskEvents = Events<Task>;
// { titleChanged: { from: string; to: string }; doneChanged: { from: boolean; to: boolean } }
```

## 24.4 Building custom utility types

The standard library can't cover everything. With mapped types, conditional types, and `infer`, you can write the missing pieces. Four that real codebases keep reinventing:

```ts
// 1. ValueOf: the union of an object's value types (the sibling of keyof)
type ValueOf<T> = T[keyof T];
const LEVELS = { low: 1, high: 3 } as const;
type Level = ValueOf<typeof LEVELS>; // 1 | 3

// 2. PartialBy: make only SOME keys optional
type PartialBy<T, K extends keyof T> = Omit<T, K> & Partial<Pick<T, K>>;
type NewTask = PartialBy<Task, "done">; // title required, done optional

// 3. RequireAtLeastOne: an object where one of the keys must be present
type RequireAtLeastOne<T> = {
  [K in keyof T]-?: Required<Pick<T, K>> & Partial<Omit<T, K>>;
}[keyof T];

type Filter = RequireAtLeastOne<{ status: string; assignee: string }>;
const f1: Filter = { status: "todo" };  // ✅
const f2: Filter = {};                  // ❌ Type '{}' is not assignable to type 'Filter'.
```

`RequireAtLeastOne` is the interesting one. For each key it builds "this key required, the others optional", and then `[keyof T]` at the end turns that object of variants into a **union** of them. Those two moves (build an object with one entry per variant, then index it to get the union) are a common idiom.

The fourth is recursive: `DeepPartial` makes every property optional at every depth.

```ts
type DeepPartial<T> = T extends object
  ? { [K in keyof T]?: DeepPartial<T[K]> }
  : T;

interface Settings { ui: { theme: string; density: number }; limits: { tasks: number } }

const patch: DeepPartial<Settings> = { ui: { theme: "dark" } }; // ✅ no density, no limits
```

This is a *preview* version. It treats arrays and functions as plain objects, which is wrong for a production utility, and that is a good illustration of why custom types need tests.

## 24.5 Testing custom types

A type with no test is a type nobody dares change. Types are testable: write assertions that must compile, and use `@ts-expect-error` for things that must **not** compile. The assertions below use `expectTypeOf`, which Vitest ships ([Chapter 27](/chapter/27) covers it in depth):

```ts
import { expectTypeOf, test } from "vitest";

test("PartialBy makes only the chosen keys optional", () => {
  type Task = { id: string; title: string; done: boolean };
  type Result = PartialBy<Task, "done">;

  expectTypeOf<Result["done"]>().toEqualTypeOf<boolean | undefined>();
  expectTypeOf<Result["title"]>().toEqualTypeOf<string>();

  // @ts-expect-error: title must still be required
  const bad: Result = { id: "1", done: true };
});
```

If `PartialBy` is later "improved" and stops requiring `title`, the `@ts-expect-error` line stops being an error, and TypeScript itself reports `Unused '@ts-expect-error' directive.` The test fails *because the type got looser*. No test runner is needed for that part: the type checker is the test runner.

```ts
// A tiny runner-free helper, if you have no test framework:
type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends (<T>() => T extends B ? 1 : 2) ? true : false;

type Expect<T extends true> = T;
type _t1 = Expect<Equal<ValueOf<{ a: 1; b: 2 }>, 1 | 2>>; // ✅
type _t2 = Expect<Equal<ValueOf<{ a: 1; b: 2 }>, 1>>;     // ❌ Type 'false' does not satisfy the constraint 'true'.
```

Think of type tests as **specifications**: a short list of "this input gives this output" examples that document the intent and guard against regressions.

## 24.6 The complexity budget

Every clever type is a loan against your teammates' time. A custom utility pays for itself when it is used in many places, replaces repeated boilerplate, and *fails with a readable error*. It doesn't pay for itself when only one file uses it, when its error messages are walls of nested conditionals, or when it slows the editor.

Compare two ways to type an emitter:

```ts
interface EventMap {
  "task:created": { task: Task };
  "task:deleted": { id: string };
}

class Emitter<M> {
  private handlers: { [K in keyof M]?: ((payload: M[K]) => void)[] } = {};

  on<K extends keyof M>(event: K, handler: (payload: M[K]) => void): void {
    (this.handlers[event] ??= []).push(handler);
  }

  emit<K extends keyof M>(event: K, payload: M[K]): void {
    this.handlers[event]?.forEach((h) => h(payload));
  }
}

const bus = new Emitter<EventMap>();
bus.on("task:created", ({ task }) => console.log(task.title)); // ✅ payload inferred from the name
bus.on("task:create", () => {}); // ❌ Argument of type '"task:create"' is not assignable to parameter of type 'keyof EventMap'.
bus.emit("task:deleted", { id: 1 }); // ❌ Type 'number' is not assignable to type 'string'.
```

This uses *one* mapped type and one generic constraint, and it solves the opening problem completely. A version that parses event names with `infer` to derive payloads from string patterns would be more "clever" and far harder to debug. A rule of thumb: **if a teammate can't read it in 30 seconds, it needs a name, a comment, a test, or deletion.**

> 🚫 **When not to.** Don't build a type-level program to avoid writing three lines of runtime code. Types should clarify intent, not become a second, untestable codebase.

## Common mistakes

> ⚠️ **Union explosion.** Interpolating several large unions multiplies members. A template with three ten-member unions is 1,000 types; with more, the compiler slows down or errors with "Expression produces a union type that is too complex to represent."

> ⚠️ **Forgetting `string & K`.** In a key-remapping template, `K` could be a number or symbol, so `` `on${K}` `` is an error. Write `string & K` to keep only string keys.

> ⚠️ **Custom utilities without tests.** `DeepPartial` quietly mishandles arrays and `Date`. Write the examples that must work, and the ones that must fail.

> ⚠️ **Cleverness for its own sake.** If the clever type has worse error messages than the plain interface it replaced, the plain interface wins.

## When to use it, and when not to

> ✅ **Use it when** string names have real structure that bugs hide in (event names, route paths, handler names), or when one utility replaces the same boilerplate in many places.

> 🚫 **When not to.** If a teammate cannot read it in 30 seconds, it needs a name, a comment, a test, or deletion. Prefer a plain union of literals when there are only a few names.

## Key takeaways

- Template literal types build string types from other types, and unions multiply into every combination.
- `Uppercase`, `Lowercase`, `Capitalize`, and `Uncapitalize` transform string literal types.
- With `as` in a mapped type, template literals generate whole families of property names from one source type.
- Custom utilities (`ValueOf`, `PartialBy`, `RequireAtLeastOne`, `DeepPartial`) are built from mapped types, conditionals, and `infer`.
- Type tests (`expectTypeOf`, `@ts-expect-error`) are specifications that stop a type from silently loosening.
- Every clever type has a cost. Keep the ones that pay for themselves, and name, comment, test, or delete the rest.
